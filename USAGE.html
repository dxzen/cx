CX usage map · source based

CX ≈ OpenSpec + Superpowers , 是一个同时兼容 Codex CLI 与 Claude Code 的轻量 AI 编程工作流插件

CX 把一次代码变更拆成可验证的阶段：先确认可观察行为，再写变更契约和任务清单，按 TDD 实现，最后用验证证据、审查结论、长期规格同步和归档收尾。
CX 不是让内部脚本替代 AI，而是让每个 Skill 节点规定：读什么、写什么、什么时候必须停、什么时候可以进入下游。AI 执行判断和编码，用户确认目标与关键取舍，CX 产物与门禁负责把过程固定下来。

设计理念

CX 源码中的核心设计是“阶段协议”：每一步都必须有输入、产出、校验与下一步，而不是把所有判断留在长上下文里。


01

规范先行

Normal/Large 先写 `contract.md`，用 Requirement 与 Scenario 固定行为。

02

最小必要流程

Micro 可轻量处理；Normal 需要契约、任务和证据；Large 增加设计或隔离。

03

TDD 铁律

`build` 明确禁止没看到 RED 失败就写 production code。

04

证据闭环

`verify` 必须写 fresh verification，`review` 必须给唯一 Decision。

05

长期事实

`sync` 把本次 spec delta 合入 `.cx/specs/`，后续需求默认读取它。

运行机制概述

CX 由 Skill、落盘产物、确定性门禁三层组成。Skill 决定 AI 行为，Markdown 产物压缩上下文，内部脚本只做可重复校验和状态推断。

Skill 层

`skills/*/SKILL.md` 规定节点读取物、停止条件、输出结构和用户确认点。

产物层

`.cx/changes/<id>/` 保存每个阶段的上下文账本，下游只读落盘文件。

门禁层

`scripts/cx.js` 校验章节、任务进度、PASS/FAIL、Decision、spec 状态和路径安全。

清理策略

Contract、Visual、Design、Tasks、Verify、Review 后都建议清理上下文，让下游依赖产物。

完整流水线

主线从 `work` 到 `archive`。Bug、UI、技术设计、worktree 是源码定义的条件分支；`status` 与 `validate` 是跨节点辅助 Skill。

流程概要说明

Skill/CX 负责

  • 定义每个阶段的职责、读写文件和停止条件。
  • 用内部门禁阻塞缺章节、缺 RED/GREEN、FAIL、pending sync、非 PASS review。
  • 通过 `.cx/specs/` 和 archive 区分长期事实与历史账本。

AI 负责

  • 澄清需求、写 contract/tasks/evidence/review。
  • 按 RED -> GREEN -> REFACTOR 实现并汇总验证。
  • 发现冲突时停下说明，而不是静默猜测。

用户负责

  • 给出目标、补充阻塞信息、确认 UI 或技术取舍。
  • 在归档、worktree、final 原型等关键点做确认。
  • 决定 warning 或剩余风险是否可接受。
